## 2. リポジトリ方針（単一 vs 分割）

### 2.1 比較

| 方式 | 向くケース | 個人検証での評価 |
|------|------------|------------------|
| **単一リポジトリ** + `frontend/` `backend/` | 一人〜少人数、フルスタックを同じサイクルで触る | **推奨** |
| **frontend / backend を別リポジトリ** | 別チーム・別法人・公開範囲を厳密分離 | オーバーヘッドが大きい |

### 2.2 結論

- **現時点は単一リポジトリ**とする（仕様書 §2.5 と同旨）。正式な記録は [ADR-001](./adr/ADR-001-single-repository.md)。
- **将来**、フロントのみ OSS 化する、バックエンドだけ別契約で運用する、といった理由が付いた時点で分割を検討する。

## 3. ディレクトリ構成（目標）

```
（リポジトリルート）
├── frontend/          # Next.js（Vercel 想定）
├── backend/           # FastAPI（Railway 想定）
├── docs/              # 仕様・運用コスト・本書 等
├── .env.example       # キー一覧（秘密は含めない）
└── README.md          # 起動手順・環境変数の説明
```

- **モノレポ用**のルート `package.json` / `Makefile` / `docker-compose.yml` は、導入する場合のみ追加する（必須ではない）。

## 4. 環境変数（.env）管理

### 4.1 原則

1. **秘密情報はリポジトリに含めない**（`.gitignore` に `.env`、`.env.local`、`.env.*.local` を含める）。
2. **`.env.example`** に「必要なキー名」と「説明コメント」のみをコミットする。
3. **フロントに渡してよい値だけ** `NEXT_PUBLIC_` を付与する。**AWS アクセスキー・長期クレデンシャルはフロントに置かない**（バックエンド経由で Bedrock を呼ぶ）。
4. **本番・Vercel / Railway** では各プラットフォームの Environment Variables に同じキーを登録する。

### 4.2 キー例（実装時に精査）

| 区分 | 例（名前は実装で確定） | 置き場所 |
|------|------------------------|----------|
| AWS | `AWS_REGION`、`BEDROCK_MODEL_ID` 等。認証は **IAM ロール（推奨）** またはバックエンドのみが読む一時クレデンシャル | `backend` のみ |
| Supabase | `SUPABASE_URL`、`SUPABASE_ANON_KEY`（検証用）、将来のサービスロールはバックエンドのみ | フロントは ANON のみ可。サービスキーは backend のみ |
| API 基底 URL | `NEXT_PUBLIC_API_BASE_URL` | frontend |
| 管理画面 | `ADMIN_COST_DASHBOARD_SECRET`（Route Handler 保護用トークン等） | **Vercel / `frontend` のサーバ専用**（`NEXT_PUBLIC_*` にしない） |

## 5. アーキテクチャ概要（論文アプリ + コスト管理）

```
[ユーザー] → Vercel(frontend) → Railway(backend) → Bedrock / S3
                              ↘ Supabase（DB、認証は後回し）
[開発者]   → 管理画面・コスト API（同一 frontend の Route Handler + /admin/cost 等）
```

- **コスト集計の HTTP API**は **Next.js の Route Handler のみ**に置く（秘密は **Vercel のサーバ環境変数**のみ）。FastAPI 側にはコスト用エンドポイントを **増やさない**（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。

### 5.1 アーキテクチャ特性・Quantum・ADR（software-architecture）

| 観点 | 本フェーズの置き方 |
|------|-------------------|
| **アーキテクチャ量子** | デプロイ単位は **Vercel（frontend）+ Railway（backend）** の 2 つだが、**ドメイン上は 1 プロダクト**として扱う。**個人検証では Quantum を実質 1 として設計し、モジュール境界はリポジトリ内の `frontend/` / `backend/` で表現**する（過早なマイクロサービス分割はしない）。 |
| **優先する特性（例）** | **Deployability**（小さく早くデプロイ）、**Maintainability**（一人で追える）、**Cost awareness**（Bedrock・各 SaaS）、**Security**（秘密はバックエンド寄り）。特性は 7 個以内に抑え、全部最適を狙わない。 |
| **ADR** | 採用済み一覧は [docs/adr/README.md](./adr/README.md)。新規判断も **1 決定 1 ADR** で追記する。形式は **Context / Decision / Consequences / Alternatives** でよい。 |
| **フィットネス関数（CI の最低ライン）** | 例: `tsc --noEmit`（または `next build`）、**Python は `pytest` + 型チェック（Pyright / mypy のいずれか）**、秘密のリーク検知（`git grep` や gitleaks 等は任意）。 |

### 5.2 フロントエンド（Effective TypeScript）

| 原則 | 実装への落とし込み |
|------|-------------------|
| **strict** | `tsconfig` で **`strict` 相当をオン**。新規コードは **`any` を使わない**（外部 JSON は **`unknown` + 実行時検証**）。 |
| **API 契約** | フロントとバックエンドで共有する **リクエスト/レスポンス型**をどこか一箇所に正とする（例: 手書きの `packages/shared-types`、または **OpenAPI から生成**。**二重管理のまま放置しない**）。 |
| **判別可能なユニオン** | コスト行・同期ジョブなど、**「手入力」「同期済み」「失敗」**のように **無効な組み合わせが表現できない型**を優先する（`status` ディスクリミネータ）。 |
| **enum の回避** | 文字列リテラルの **ユニオン型**（例: サービス識別子を `'vercel'` と `'railway'` などのリテラルで表す）を優先する。 |
| **外部 Billing API** | `fetch` の結果を **`as` 一発で信頼しない**。**Zod `safeParse`** 等で絞り込み、失敗時は UI で明示（§6.2 のフォールバックと整合）。 |
| **公開 API** | コンポーネントの **Props・Route Handler の戻り値**は、呼び出し側が迷わないよう **明示的に型を書く**。 |

### 5.3 バックエンド（robust-python）

| 原則 | 実装への落とし込み |
|------|-------------------|
| **型** | FastAPI でも **引数・戻り値に型**を付ける。**`Any` は原則禁止**（やむを得ない場合はコメントで理由）。 |
| **境界** | リクエストボディ・クエリは **Pydantic モデル**で受け、**ドメインに入る前に検証**する。 |
| **コストプロバイダ** | F4-3 第 2 段階の自動取得は **[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)** のとおり **`frontend` の server-only（TypeScript）**で実装する。Python バックエンドには **コスト用アダプタを置かない**。TS 側で **インターフェース分割と Fake 差し替え**を行う。 |
| **結果型** | 外部 API は失敗しうるため、**例外だけに頼らず**、戻り値で **`成功 | 失敗理由`** を表現する型（ユニオンや Result パターン）を検討する。 |
| **セーフティネット** | **pytest** を M0〜M1 で最低 1 本（ヘルスチェック等）から回せるようにし、**Pyright / mypy** を CI か pre-commit のどちらかに載せる。 |

### 5.4 Railway デプロイ・設定（use-railway）

| 項目 | 指針 |
|------|------|
| **リソースモデル** | **Workspace → Project → Environment → Service**。変数・デプロイ履歴は **Environment / Service 単位**で異なる。 |
| **モノレポ** | `backend/` のみを Railway サービスに載せる場合、ダッシュボードまたは設定で **Root Directory** を **`backend`** に合わせる（CLI・ドキュメントの **monorepo / Dockerfile** 手順に従う）。 |
| **変数** | ローカル `.env` と **Railway Variables** の **キー名を揃える**。変更後は `railway variable list --json`（またはダッシュボード）で読み戻し確認。 |
| **コンテキスト** | スクリプトや手順書では **`railway status --json`** / **`railway whoami --json`** で接続先を確認する。URL から ID を貼る場合は **その URL のプロジェクト/サービスが正**とし、**グローバル link と取り違えない**。 |
| **運用コマンド** | ログ確認: `railway logs --lines 200`、複数サービス時は **`--service`** を明示。破壊的操作前に **読み取りコマンドでスコープを再確認**する。 |

## 6. 運用コスト管理画面（F4-3）の段階実装

運用コスト.md §1.1 のとおり、**完全な一元ダッシュボードは各社に存在しない**。実装は段階に分ける。

### 6.1 第 1 段階（MVP・推奨で最初に実装）

| 内容 | 説明 |
|------|------|
| **サービス別カード** | Vercel / Railway / Supabase / AWS の名称、**公式 Billing URL**（運用コスト §1.1 の表と同趣旨） |
| **手入力** | 月次の **USD 概算**、メモ、更新日 |
| **合計** | 画面上で単純合算（為替は手入力か固定レートを注記） |
| **永続化** | 個人検証では **Supabase のテーブル 1 枚** または **JSON ファイル（コミットしない）** でよい |

**メリット**: 実装が軽く、[運用コスト.md](./運用コスト.md) の運用リズム（月 1 回各所を開く）を**記録に残せる**。

### 6.2 第 2 段階（自動取得・任意）

| データ源 | 概要 | 注意 |
|----------|------|------|
| **AWS** | Cost Explorer API / CUR（要 IAM、集計に遅延あり） | 権限設計が重い。まずは **Bedrock・S3 にタグ**を付け按分しやすくする |
| **Vercel** | Team Billing API（プラン・トークン要確認） | 利用可能エンドポイントは [公式ドキュメント](https://vercel.com/docs) で確認 |
| **Railway** | GraphQL / 請求 API（変更容易） | 仕様変更時に追従コスト |
| **Supabase** | Management API / `get_cost` 等（**organization コンテキスト**が必要な場合あり） | 実装前にドキュメントで必須パラメータを確認 |

**方針**: **Next.js サーバ側**（Route Handler から呼ぶモジュール）に **プロバイダ別アダプタ**を置き、取得失敗時は第 1 段階の手入力にフォールバックする（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)・[ADR-004](./adr/ADR-004-f4-3-phased-delivery.md)）。

### 6.3 アクセス制御（認証保留中）

- **URL を推測されにくくする**、`Authorization: Bearer <長いランダム>` を必須にする、**Vercel のプレビューをオフ**にする、など [仕様書 §3.5 F4-3](./仕様書.md) に沿う。
- **本番で複数ユーザー**が使る段階では、**必ずログイン後のみ**管理画面にアクセス可能にする。

### 6.4 UI / UX 方針（ui-design・front-design・ux-psychology）

管理画面は**メインの論文 UI と競合しない**よう、情報設計とビジュアルを分ける。

| 観点 | 方針 |
|------|------|
| **認知負荷（Miller / Hick）** | **サービス別カード**でチャンク化し、**1 画面の主要アクションは 1〜2 個**（例: 「保存」「公式を開く」）。自動同期オプションは第 2 段階で **段階的開示**する。 |
| **メンタルモデル（Jakob）** | 各カードに **公式 Billing への明確なラベル付きリンク**を置き、「この数字はダッシュボード上のどれに相当するか」を短い注記で補う（[運用コスト.md](./運用コスト.md) §1.1 の運用と一致）。 |
| **操作（Fitts）** | タブレット利用（仕様書 1.3）を意識し、**タップターゲットを十分なサイズ**に保つ。 |
| **ピーク・終了（Peak–End）** | 月次金額の**保存成功**時に、軽い確認表示（トースト等）で**終了体験をポジティブ**にする。 |
| **美的・テンプレ感（Aesthetic / AI slop 回避）** | **学術・読書 UI とは別トーン**でもよいが、**汎用の紫グラデ・テンプレダッシュボード**に収束させない。**コンセプトキーワード**（信頼・可読性・落ち着き）を 1 行で決め、[front-design](../.cursor/skills/front-design/SKILL.md) の **カラー/タイポの体系**に沿ってトークン化する。 |
| **モーション** | `prefers-reduced-motion` を尊重する。ロード中は **スケルトンや短いフェード**（[ui-design](../.cursor/skills/ui-design/SKILL.md) のモーション節）で **Doherty 閾値**付近の体感を改善。 |
| **空の状態** | 未入力の月は **イラスト必須ではないが**、「まずは公式を開いて金額をメモ」等の **Empty state 文案 + 一次 CTA** を置く。 |
| **倫理** | コスト表示は **脅しや過度な不安喚起**に使わない（数値は事実、コピーは中立）。 |

## 7. 認証・認可を保留する場合の実装指針

| 論点 | 指針 |
|------|------|
| **会話履歴・DB** | **単一テナント**として設計。`user_id` カラムは **NULL 固定またはダミー 1 件**でもよい（後で Supabase Auth と接続しやすい形にする）。 |
| **API** | 開発時は **環境変数の共有シークレット**で `/api/*` をガードする、など最小限の対策を検討（公開デプロイ時）。 |
| **本番移行** | 仕様書 §2.6 のとおり、**不特定多数に公開する前**に F4-2 を実装し、非機能のセキュリティ要件を満たす。 |

## 8. マイルストーン案（個人検証）

| 順序 | 目標 | 主な成果物 |
|------|------|------------|
| M0 | 足場 | `frontend/` `backend/` 作成、`.env.example`、README、Git 除外設定 |
| M1 | 疎通 | ローカルで Next.js ↔ FastAPI 疎通、Railway / Vercel に空デプロイ（Railway は **rootDirectory**・**Variables**・`railway status --json` でコンテキスト確認） |
| M2 | AI | バックエンドから Bedrock（要約または短いチャット）成功 |
| M3 | コア UI | PDF 表示（最低限）、アップロード or URL 取得の仮実装 |
| M4 | コスト | F4-3 第 1 段階（リンク + 手入力 + 合計） |
| M5 | MVP 寄せ | 仕様書 Phase 1 の要約・Q&A をつなぐ（認証なし） |

期間は仕様書 §6 の Phase 1（2〜3 週間）を目安に、**コスト画面は M4 で並行**可能。
