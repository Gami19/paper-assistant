## 1. フロントの論理構成（software-architecture）

| 観点 | 方針 |
|------|------|
| **量子との関係** | フロントは **Vercel 上の 1 デプロイ単位**として扱う。ドメインはメインの論文 UI と **管理（コスト）UI** の 2 系統があるが、**同一アプリ内のルート／レイアウト分割**で表現し、過早なマイクロフロントエンド化はしない。 |
| **レイヤリング** | **表示（ページ・コンポーネント）**、**データ取得（サーバー側 Route Handler またはクライアントの薄いフック）**、**ドメインに近い型・検証**の責務を混同しない。外部 JSON は **境界で検証**し、コンポーネント深部に `unknown` を垂れ流さない。 |
| **同期通信をデフォルト** | メイン機能は **リクエスト／レスポンス**で十分な範囲から始める。リアルタイムや複雑なオフラインは MVP 外なら ADR なしで「やらない」と決めてよい。 |
| **ADR が効くタイミング** | コスト API は **[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)** で Route Handler 固定。**PDF 表示ライブラリの選定**、**クライアント状態管理の導入有無**などは従来どおり ADR 候補。索引は [docs/adr/README.md](./adr/README.md)。 |

## 2. メイン UI と管理 UI の分離（UX / ビジュアル戦略）

| 領域 | 役割 | ux-psychology | front-design / ui-design |
|------|------|---------------|---------------------------|
| **メイン（論文読解）** | PDF 主・チャット副（仕様書 §5.1）。**深い読解**がゴール。 | **Jakob**: 読書・PDF アプリに近い配置（ビューアの主役、チャットは補助）。**Miller**: チャンクは「ページ／選択範囲／会話ターン」。**Doherty**: AI 待ちは構造が分かる待機 UI。 | **操作系は標準準拠**（スクロール、選択、送信の近接）。**表現系**で学術・落ち着きのトーン（テーマを 1 つ決め、トークン化）。**AI slop**（汎用ダッシュボード風）に寄せない。 |
| **管理（F4-3 コスト）** | 開発者向け・頻度は低い。 | **Hick / Miller**: サービス別カードでチャンク、主要 CTA は 1〜2。**Peak–End**: 保存成功の軽いフィードバック。**倫理**: コストは脅し文句に使わない。 | メインと**視覚的に区別**してよいが、**別プロダクトのテンプレ**に見えないようコンセプトキーワードを文書化。**WCAG AA**・**タップターゲット**（仕様書 1.3 タブレット）を満たす。 |

## 4. フェーズ別ガイド（コードなし）

### FE-0：足場（M0）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | `frontend` が単体で `build` できる状態。環境変数の読み分け（公開可のみ `NEXT_PUBLIC_*`）を README と揃える。 |
| **effective-typescript** | `strict` 相当を有効にする方針を決める。新規ファイルから **`any` 禁止**を徹底。 |
| **ui-design** | グローバルな **スペーシングスケール**・**カラー層（Primary / Neutral / Semantic）** の方針だけ決め、ページはプレースホルダでよい。 |
| **完了条件** | CI またはローカルで **型チェック**が通る。秘密がコミットされない。 |

### FE-1：疎通（M1）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | 「フロント → バックエンド」の **単一の健全性チェック**（例: `/health` 表示）を 1 画面または開発用ルートに置く。 |
| **effective-typescript** | API レスポンス型を **どこに正として置くか**（共有パッケージ／生成／手書きのいずれか）を決め、**二重定義を防ぐルール**をメモする。 |
| **ux-psychology** | 失敗時（オフライン・500）に **支援的なコピー**で理由と次の一手を示す（Postel / エラー感情の軽減）。 |
| **完了条件** | 本番相当の URL で **フロントからバックエンド到達**が確認できる。 |

### FE-2：AI 表示の最小経路（M2）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | チャット 1 往復分の **データフロー**（入力 → 送信 → ストリーミング or 一括）を一本に絞る。 |
| **effective-typescript** | ストリームやチャンクを扱う場合、**状態を判別可能なユニオン**（待機中／ストリーム中／完了／エラー）で表現する。 |
| **ux-psychology** | **Doherty**: 400ms を超えそうならスケルトン・進捗。**Tesler**: ユーザーに不要な再入力をさせない。 |
| **ui-design** | 送信・中断（あれば）の **アクション階層**を明確に。`prefers-reduced-motion` を設計に含める。 |
| **完了条件** | バックエンド経由で **1 回以上**エンドツーエンドで応答が表示される。 |

### FE-3：PDF 主・チャット副（M3）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | レイアウトを **「ビューア領域」「補助（チャット）領域」** に分割し、後から認証やサイドバー追加で崩れにくい依存方向にする。 |
| **effective-typescript** | 選択範囲・ページ番号など **ドメイン識別子**は素の `number` だけに頼らず、意味が分かる型（ブランド型やリテラル付きオブジェクト）を検討。 |
| **ux-psychology** | **Fitts**: ツールバー・チャット送信のターゲットサイズ。**Jakob**: 既存 PDF リーダの期待に沿ったズーム・ページ移動。 |
| **front-design / ui-design** | メイン画面用の **タイポ階層（Primary / Secondary / Tertiary）** と、長文本文の **行長（約 45〜75 文字相当）** を意識。 |
| **完了条件** | **PDF が主役**で表示され、チャットが **同画面内の副位置**に存在する。 |

### FE-4：運用コスト管理 F4-3 第 1 段階（M4）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | 管理ルートは **メインのルートツリーと視覚的・論理的に分離**。**コストの CRUD・合計は Route Handler** に集約し、FastAPI には寄せない（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。秘密トークンは **Vercel のサーバ環境変数のみ**（実装計画 §4・§6.3）。 |
| **effective-typescript** | サービス行・月次行を **判別可能なユニオン**で表現。合計は **表示用の導出**とソースデータを混同しない。 |
| **ux-psychology** | **Von Restorff**: 強調は 1〜2 箇所。**Empty state** と公式 Billing への **明示ラベル付きリンク**。 |
| **front-design** | 管理画面用に **短いビジュアル戦略**（キーワード 3〜5、禁止パターン: 紫グラデ乱用等）を 1 ページでよいので残す。 |
| **完了条件** | [実装計画.md](./実装計画.md) §6.1 の **カード・手入力・合計・永続化方針**を満たす。 |

### FE-5：MVP 寄せ（要約・Q&A）（M5）

| 観点 | やることの例 |
|------|----------------|
| **architecture** | F1 系機能を **画面フロー**（アップロード → 読解 → 要約／Q&A）でつなぎ、**画面間で持ち越す状態**を最小化。 |
| **effective-typescript** | 要約・Q&A の **API 契約**を FE-2 で決めた正に収める。**Zod 等での境界検証**を欠かさない。 |
| **ux-psychology** | **Peak–End**: 要約完了や Q&A 成功時の終了体験。**認知負荷**: 結果が長い場合は折りたたみ・見出し。 |
| **ui-design** | 結果表示は **テーブル／リストの数値右揃え**等、読みやすさの細部を仕様書の MVP と照合。 |
| **完了条件** | 仕様書 **MVP（Phase 1）** のフロント側要件を満たす（認証は引き続き保留でよい）。 |

## 5. 第 2 段階（コスト自動取得）をフロントに載せるとき

実装計画 §6.2 の **プロバイダ別アダプタ**は、**同一 `frontend` の server-only（TS）**に置く（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。Route Handler／UI 側では次を満たす。

| 観点 | 方針 |
|------|------|
| **architecture** | 「同期ボタン」「最終取得時刻」「失敗時は手入力へフォールバック」を **同一画面の段階的開示**で足す（Hick）。 |
| **effective-typescript** | 自動取得結果は **成功／部分成功／失敗**を型で分け、UI を switch で網羅（`never` チェック推奨）。 |
| **ux / ui** | プロバイダ障害時は **中立なコピー**で再試行と手入力を並記（倫理・信頼）。 |

## 6. フィットネス関数（フロント）

| タイミング | 例 |
|------------|-----|
| **コミット前／CI** | `tsc --noEmit` または `next build`、Lint、**秘密文字列の静的検査**（任意）。 |
| **レビュー時** | effective-typescript スキルの **Slop チェック**（判別ユニオン乱用・`Record<string, unknown>` 逃げ等）を意識。 |
| **UI レビュー時** | ui-design の **階層・スペーシング・コントラスト・モーション（reduced-motion）**、ux-psychology の **操作系／表現系のバランス**。 |
