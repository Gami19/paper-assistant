# ADR-003: Phase 1 で認証・本格認可を保留する

## Status

Accepted

## Context

- [仕様書.md](../仕様書.md)・[実装計画.md](../実装計画.md) は **個人検証・非商用**を前提とし、**MVP（Phase 1）**で **ログイン UI・Supabase Auth の本格実装を行わない**としている。
- 一方で、**本番 URL にデプロイ**する場合、**無防備な管理画面・API**はリスクになる。

## Decision

**Phase 1 では「本格的な認証・認可（ユーザー登録・ロール・RLS 前提のマルチテナント）」を実装しない。** 代わりに次を満たす。

- **単一テナント**としてデータを扱う（`user_id` は NULL 固定やダミー 1 件でもよい、[実装計画.md](../実装計画.md) §7）。
- **公開デプロイ時**は、管理機能・機密 API について **環境変数ベースの共有シークレット**（Bearer 等）、**推測困難なパス**、**プレビュー環境の制限**など **最小限のガード**を講じる（§6.3・仕様書 F4-3）。
- **不特定多数に公開**する前に、仕様書 §2.6 に従い **F4-2 等のセキュリティ要件**を満たす段階で **本 ADR を Supersede する新 ADR** を立て、認証を必須化する。

## Consequences

### ポジティブ

- MVP までの **実装スコープと学習コスト**を抑えられる。
- 後から Auth を足すときの **データモデル拡張**の余地を §7 で明示している。

### ネガティブ

- **シークレット流出・URL 推測**に対する防御は **本格認証より弱い**。運用上 **ローテーション・最小共有**を徹底する必要がある。

## Alternatives

| 案 | 却下理由（Phase 1） |
|----|---------------------|
| **最初から Supabase Auth 完備** | **納期・検証目的**に対して重い。 |
| **認証なしで管理画面を完全公開** | リスクが高すぎる。**最小ガードは必須**（§6.3）。 |

## Compliance

- 管理系 Route Handler・API には **認証ヘッダ必須**など、仕様書・実装計画 §6.3 のチェックリストをレビューに含める。
- 「公開 beta」等の段階移行時に **再評価**し、未達なら公開範囲を狭める。
