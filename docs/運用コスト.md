# 運用コスト（見積もり・監視のたたき台）

本ドキュメントは [仕様書.md](./仕様書.md)（v3.2 想定）の技術構成に沿った運用費の整理です。**主題は「A. 個人検証・非商用」で開発を進める場合**（開発者少数・デモ止まり・収益化しない想定）の**月額イメージ・無料枠の落とし穴・最低限の監視**です。**サービス別の単価メモは §3〜§6**、**仕様書のコスト試算との突き合わせ・本番寄りシナリオは §7**、**汎用の監視チェックリストは §8** にまとめています。

**注意**

- 料金・無料枠は変更されます。**見積もり・契約前に必ず各公式の Pricing を確認**してください。
- 下記のうち **AWS** については [Amazon Bedrock Pricing](https://aws.amazon.com/bedrock/pricing/)・[S3 Pricing](https://aws.amazon.com/s3/pricing/) の**公式ページ取得**および **MCP**（`user-aws-knowledge-mcp` の `aws___search_documentation`）で裏取りした内容を、**2026-04-11 時点の参照メモ**として記載しています。**Supabase** の超過単価は [About billing on Supabase](https://supabase.com/docs/guides/platform/billing-on-supabase) の表に基づきます。**Vercel / Railway** は [vercel.com/pricing](https://vercel.com/pricing)・[railway.com/pricing](https://railway.com/pricing) を **Web 参照**（いずれも更新頻度が高いため、確定額は各ページとダッシュボードを正とする）。

### 1.0 仕様書（ドキュメント検索）との突き合わせ

[仕様書.md](./仕様書.md) **§4 非機能要件**では、応答速度・同時接続（〜10 名）・**コスト目標（月額 50 USD 以下）**が定義され、**コスト試算**として Vercel / Railway / Supabase / Bedrock のレンジが示されています。本書の **§2** は個人検証での実務的な足し算、**§3 以降**は単価メモと本番寄りの試算で、そのレンジが**どの公開料金から概算可能か**を示すためのものです。実装で **論文 PDF を S3 と Supabase のどちらに置くか**が決まると、**S3 ストレージ＋GET** と **Supabase Storage＋Egress** のどちらが効くかが変わるため、試算時に分岐させてください（仕様書 §2.1 の「S3 / Supabase」併記と整合）。

### 1.1 全サービスの料金を「一括ダッシュボード」で見たい場合

**前提**: 上表のサービスは **請求主体がそれぞれ別**（AWS / Vercel / Railway / Supabase）です。いずれか1社の公式ダッシュボードだけで **他社分の請求まで自動表示されることは基本的にありません**。

| やり方 | 内容 | 向き |
|--------|------|------|
| **A. 各公式の Billing を1ページに集約（リンク集）** | 月次で「今月の請求額」を目視し、必要ならスプレッドシートや Notion に転記する。**実装コストゼロ**で確実。下表の URL をブックマークする。 | 個人開発〜小規模チームの定番 |
| **B. マルチクラウド／SaaS 向けの第三者ダッシュボード** | 複数アカウントの請求・利用量を **API 連携で集約**する FinOps 系プロダクト（連携対象は製品ごとに異なる。多くは **有料** かつ **各サービスへの読み取り権限**が必要）。導入前に **Vercel / Railway / Supabase が公式連携に対応しているか**を必ず確認する。 | 支出が大きくなり、監査や按分が必要になった段階 |
| **C. AWS 中心に分解する** | 変動費の大半が **Bedrock・S3** になる想定なら、[AWS Cost Explorer](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html) と **予算アラート**で AWS 内を細かく見る。Vercel / Railway / Supabase は **サブスク＋ダッシュボードの月次確認**に分ける。 | 仕様書の「Bedrock がコスト感度大」に合わせた運用 |

**各サービスの請求・利用量（公式ダッシュボード）への導線**

| サービス | 確認先（目安） |
|----------|----------------|
| **Vercel** | チームの **Settings → Billing**（[ドキュメント内の Billing 説明](https://vercel.com/docs/limits) からダッシュボードへ） |
| **Railway** | アカウントの **Usage / Billing**（[Pricing](https://railway.app/pricing) およびログイン後のワークスペース） |
| **AWS（Bedrock・S3 含む）** | [AWS Billing and Cost Management](https://console.aws.amazon.com/billing/) の **Cost Explorer**・請求書。サービス別フィルタで Bedrock / S3 を分離可能（タグ設計があると按分しやすい）。 |
| **Supabase** | Organization の **[Billing](https://supabase.com/docs/guides/platform/billing-on-supabase)**・**Usage**（ドキュメント記載の usage ページ） |

**自前で「1枚ダッシュボード」を作る場合**: 各社が **請求 API / エクスポート**（AWS CUR、他は CSV やメールの請求書）を提供しているので、週次バッチで数値だけ BigQuery やスプレッドシートに流す構成も可能。ただし **開発・保守コスト**がかかるため、利用者が少ないうちは **A（リンク集＋月次転記）** が費用対効果が高いことが多いです。

## 2. 個人検証・非商用での運用コスト（本書の主題）

[仕様書.md](./仕様書.md) のスタック（Vercel / Railway / Supabase / Bedrock / S3）を載せるうえで、**自分一人またはごく少人数で動作確認する段階**では、**Vercel Hobby・Supabase Free・Railway のトライアル／低額プランで固定費を抑え、コストの大半を Bedrock（必要なら S3）の従量に寄せる**形が現実的です。以下はその前提での見積もりと注意点です。

### 2.1 シナリオの前提（「個人検証・非商用」の定義）

| 項目 | 想定 |
|------|------|
| **目的** | 実装検証、UI/LLM の挙動確認、試作デモ（**不特定多数向けの商用サービスとして公開しない**） |
| **フロント** | [Vercel Hobby](https://vercel.com/docs/plans/hobby-plan)：**無料**。ただし **商用利用不可**などの制限があるため、**収益化・本番商用**に進むタイミングで **Pro 等への移行**が必要になる（§5）。 |
| **DB・認証** | [Supabase Free](https://supabase.com/pricing)：**$0**。無料プロジェクト数・各種クォータあり（§4 表）。 |
| **バックエンド** | [Railway](https://railway.com/pricing)：**トライアルクレジット**の後は、公式に記載の **月額＋含まれる利用クレジット＋従量**（金額・プラン名は更新されやすいので **ダッシュボードの Billing/Usage を正**とする）。常時高スペックにしないとクレジット内に収まりやすい。 |
| **AI・ファイル** | **Amazon Bedrock**（従量）。論文 PDF は **S3** か **Supabase Storage** のどちらか（§1.0）。 |

### 2.2 費用の出方（固定費と変動費）

**固定費に近いところ（$0 を狙うとき）**

- **Vercel Hobby**: **$0**（帯域・ビルド・関数実行が各上限内、かつ Hobby の利用条件を満たすとき）。
- **Supabase Free**: **$0**（無料枠内の利用にとどまるとき）。
- **Railway**: **$0**（トライアルクレジットのみで完結する短期間）または **公式ページの最小プラン＋クレジット**（例として **$1/月**や **$5 分の利用クレジット**等の説明が並ぶ。**最新は [railway.com/pricing](https://railway.com/pricing) で確認**）。

**変動費（個人検証でもここが本体になりがち）**

- **Amazon Bedrock**: チャット・要約・Embedding の **トークン × 単価**（§3.0・§3.1）。**高単価モデル**や**長い文脈を毎回載せる**実装だと、利用者が一人でも **月数十 USD** に届きうる。
- **Amazon S3**: PDF 数本・数百 MB 級なら **ストレージは USD 未満オーダー**になりやすい一方、**フル PDF を繰り返し配信**する実装では **GET と転送**が積み上がる（§3.2）。

### 2.3 月額イメージの例（1 開発者・非商用・概算）

以下はすべて **仮定**です。モデル・リージョン・実装で変わります。

| パターン | ざっくり前提 | ホスティング＋DB（USD/月） | Bedrock 以外の AWS | Bedrock | 合計のオーダー感 |
|----------|--------------|----------------------------|---------------------|---------|------------------|
| **軽め** | Hobby + Supabase Free、Railway はクレジット内または最小プラン、**1 日 ~20 回**程度しか LLM を呼ばない、**軽量モデル**・短文 | **$0〜5** | **≈$0**（S3 極小） | **$1〜8** 前後 | **おおよそ $1〜15** |
| **かなり触る** | 同じ基盤のまま **1 日 ~100 回**、要約・RAG 試行、**中〜高単価モデル**を多用 | **$0〜8** | **≈$0〜1** | **$15〜50+** | **$20〜60+**（**仕様書の「月額目安」は本番想定でもあるが、検証段階の Bedrock だけで超えうる**） |

**コストを抑える設計のレバー**

- **モデル階層**（安価モデルへ寄せる）、**プロンプトと RAG チャンクの短縮**、**同一論文の再 Embedding を避ける**（§3.1 の数式）。
- **Supabase Free の Egress 5 GB/月**に触れないよう、PDF 配信経路を早めに設計する（Storage からの直配信の多用は Egress が伸びやすい）。

### 2.4 無料枠・低額プランで先に詰まりやすい論点

1. **Supabase Free**: **DB 500 MB/プロジェクト**、**Egress 5 GB**、**Storage 1 GB**（§4）。会話ログ・メタデータの肥大化、PDF の置き場所と配信方法に注意。
2. **Vercel Hobby**: **ビルド分数・帯域・Serverless 実行時間**の上限。デプロイ頻度や重い関数で上限に触れうる。
3. **Railway**: **クレジット超過**後の従量、または **CPU/RAM 割当の肥大化**で請求が伸びる。**Usage は週 1 程度**見ると安心。
4. **AWS**: Bedrock は **常に無料枠が付与されるとは限らない**ため、**請求アラート**（例：$5 / $20）を早めに設定する。

### 2.5 この段階での監視（最低限）

- **AWS**: [Cost Explorer](https://docs.aws.amazon.com/cost-management/latest/userguide/ce-what-is.html) と **予算アラート**（Bedrock・S3 でフィルタ）。
- **Supabase**: Organization の [Usage](https://supabase.com/docs/guides/platform/billing-on-supabase)（Disk / Egress）。
- **Vercel・Railway**: 各ダッシュボードの Usage（§1.1 のリンク集で可）。

より詳しいチェックリストは **§8**。

### 2.6 商用・本番へ進むとき

**Vercel を商用で使う**、**Supabase を Pro に上げる**、**利用者が増える**段階では **§7** の「B. 小規模本番」および仕様書 §4 のコスト試算を主に参照してください。

## 3. Amazon Web Services（Bedrock・S3）

### 3.0 公開単価メモ（公式ページ・2026-04-11 参照）

以下は **リージョン・モデル版・課金ティア**により変動します。契約・予算の前に必ず公式表を開いてください。

| 項目 | 公開されている例（出典） | メモ |
|------|-------------------------|------|
| **Bedrock（例: Anthropic Claude 3.5 Sonnet 系・オンデマンド）** | **入力 $6.00 / 100 万トークン**、**出力 $30.00 / 100 万トークン**（**US East 等**の表記。Public Extended Access・Effective 1 Dec 2025） | [Amazon Bedrock Pricing](https://aws.amazon.com/bedrock/pricing/) の Anthropic 表。**東京リージョンを使う場合は同ページの該当リージョン列**で単価が異なることがあります。 |
| **Bedrock（Embedding・例: Amazon Titan Text Embeddings V2）** | 同一ページの **Amazon → Embedding models** に **100 万トークンあたりの入力単価**が記載（多くの公開まとめでは **約 $0.02 / 1M input** 前後とされるが、**以公式表の数値を採用**） | RAG の初回インデックス作成で一度まとまって発生しやすい。**チャンク再生成ポリシー**がコストに直結します。 |
| **S3（例: Standard・GET）** | 公式の料金例に **S3 Standard の GET: $0.0004 / 1,000 リクエスト**（リージョン例: US East） | [S3 Pricing](https://aws.amazon.com/s3/pricing/) の Storage & requests。**ストレージは GB・月単価がリージョン別**（例として同一ページ内に **S3 Tables Standard で $0.0265/GB・月**などの例示あり。通常バケットの Standard は同ページの「Storage pricing」表を参照）。 |
| **S3（データ転送）** | 公式に **インターネットへの転送アウトは月 100 GB まで無料**などの説明（リージョン・条件あり） | フロント／クライアントに PDF を直接落とす構成では転送が効きます。 |

### 3.1 Amazon Bedrock

- **料金の性質**: 利用する **基盤モデル（プロバイダー・モダリティ・リージョン）** ごとに異なり、**オンデマンド**に加え **Provisioned Throughput**、**バッチ**、**プロンプトキャッシュ** など利用形態で最適化できる、という説明が公式にあります。
- **コスト要因の例**（公式の整理に基づく概念）:
  - **推論**（入力・出力トークン、画像トークン等）
  - **RAG 関連**（Knowledge Bases のクエリ・文書処理など、利用する場合）
  - **Guardrails / 評価 / その他オプション**（利用時のみ）
- **試算の考え方（数式）**: オンデマンドなら概ね  
  **`月額（USD） ≈ (入力トークン数 / 10^6) × 入力単価 + (出力トークン数 / 10^6) × 出力単価`**（画像・キャッシュ・バッチ割引は別途）。
- **具体例（上記 Sonnet 単価を仮定した電卓のみ。実リージョン・実モデルで置き換え必須）**  
  - 1 ユーザーあたり月 200 回チャット、1 回あたり **入力 2,000 トークン・出力 500 トークン**と仮定：  
    - 月間入力: 200 × 2,000 × 10 ユーザー = **4,000,000 トークン** → 4 × $6 = **$24**  
    - 月間出力: 200 × 500 × 10 = **1,000,000 トークン** → 1 × $30 = **$30**  
    - **合計約 $54 / 月（Bedrock のみ）** → 仕様の **月額 50 USD 以下**を **Sonnet 常時・この利用量**だと超えやすい。**Haiku / Nova 等の低単価モデルへの切替**、**プロンプト短縮**、**キャッシュ**、**ルーティング**（Bedrock の Intelligent Prompt Routing の説明あり）が設計上のレバーになる、という読み取りができます。
- **推奨リソース**
  - 料金一覧: [Amazon Bedrock Pricing](https://aws.amazon.com/bedrock/pricing/)
  - 見積もり: **AWS Pricing Calculator**（公式検索結果で言及）
  - コスト最適化の考え方: [Effective cost optimization strategies for Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/effective-cost-optimization-strategies-for-amazon-bedrock/)
  - RAG チャットボットの料金イメージ: [Demystifying Amazon Bedrock Pricing for a Chatbot Assistant](https://aws.amazon.com/blogs/machine-learning/demystifying-amazon-bedrock-pricing-for-a-chatbot-assistant/)
- **本プロダクト観点**: 仕様書どおり **Embedding も Bedrock** に統一する場合、**チャット＋RAG 用 Embedding のトークン／リクエスト**の両方が変動費になります。利用モデル確定後に Calculator でシナリオ別に試算するのが確実です。

### 3.2 Amazon S3（論文 PDF 等）

- **料金の性質**: **ストレージクラス**（Standard / IA / Glacier 等）、**容量**、**リクエスト**、**データ取得**、**転送**（インターネット往復は一定無料枠の説明あり）など、複数要素の組み合わせ。
- **極小の目安（教科書的なオーダー感）**: 論文 PDF を **50 本・各 5 MB（計 250 MB）** 保存し、**Standard** に置く場合、ストレージは **サブ GB** なので **ストレージ月額は $0.1 未満オーダー**になりやすい（正確な **$/GB・月**はリージョンの表で乗算）。一方、**クライアントに毎回フル PDF を配信**すると **GET 回数と転送 GB**が乗るため、仕様の「ビューア中心」でも **キャッシュ・署名付き URL・レンジ取得**などの設計が転送費に効きます。
- **推奨リソース**: [S3 Pricing](https://aws.amazon.com/s3/pricing/)
- **本プロダクト観点**: ユーザーごとの PDF 蓄積が増えるほど **GB 月額**が伸びます。アクセス頻度が低いアーカイブはストレージクラス見直しで下げられる場合があります（要件・取得遅延とトレードオフ）。

## 4. Supabase（PostgreSQL・Auth・Storage 等）

公式の「About billing on Supabase」に、**プラン別のクォータと超過時の単価**が表形式で示されています（抜粋）。

出典: [About billing on Supabase](https://supabase.com/docs/guides/platform/billing-on-supabase)

| 利用項目 | Free | Pro / Team（含まれる量 → 超過） |
|----------|------|----------------------------------|
| Egress | 5 GB | 250 GB まで含む → 超過 **$0.09 / GB**（ドキュメント上の表記） |
| Database Size（ディスク） | **500 MB / プロジェクト** | **8 GB / プロジェクト** まで含む → 超過 **$0.125 / GB** |
| Monthly Active Users（MAU） | 50,000 | 100,000 まで含む → 超過 **$0.00325 / MAU** |
| Storage Size | 1 GB | 100 GB まで含む → 超過 **$0.021 / GB** |
| Edge Function Invocations | 500,000 | 200 万まで含む → 超過 **$2 / 100 万回** |
| Realtime Message Count | 200 万 | 500 万まで含む → 超過 **$2.5 / 100 万** |
| Realtime Peak Connections | 200 | 500 まで含む → 超過 **$10 / 1000**（ピーク接続のパッケージ課金の説明あり） |

**その他（公式ドキュメントより）**

- **組織単位の課金**: プランは **Organization ごと**。同一組織内で Free と Pro を混在させられない。
- **Free**: アクティブな **無料プロジェクトは 2 つまで**（Paused はカウント外など、詳細は同ページ）。
- **Compute**: 有料プランでは **プロジェクトごとに専用 Postgres（Compute）** が課金対象。複数プロジェクトで Compute 時間が積み上がる旨の説明あり。Billing FAQ では **Pro $25** と **Compute Credits $10**、**Micro Compute 約 $10/月相当** などの例が出てくるため、**正確な定額は [Pricing](https://supabase.com/pricing) とダッシュボード**で確認してください。
- **スペンドキャップ**: Pro では **Spend Cap** の有無で超過利用の扱いが変わる（公式 FAQ）。

**本プロダクト観点**: 会話履歴・ユーザーデータで **DB ディスク**が増え、クライアントからの API で **Egress** が増えます。仕様の「〜10 同時接続」でも、PDF 配信を Supabase Storage 経由にすると Egress に効きます。

## 5. Vercel（Next.js ホスティング）

公式ドキュメントでは **Hobby / Pro / Enterprise** などのプラン区分や、**請求・クレジット・API レート制限**に関する記述があります。具体的な月額はプロダクトの価格ページの更新が早いため、次を primary とします。

- **Pricing（公式）**: [vercel.com/pricing](https://vercel.com/pricing)
- **Web 参照メモ（2026-04-11、要ページ再確認）**  
  - **Hobby**: **無料**。ただし **商用利用不可**などの制限があるため、サービス公開形態によっては Pro 必須になり得る（[Limits / Plans ドキュメント](https://vercel.com/docs/limits) と Pricing を併読）。公開情報では **データ転送 月 100 GB 前後**、**ビルド分数**、**Serverless 実行時間**に上限がある旨の説明が多い。  
  - **Pro**: **シート課金で月額 $20 前後／開発者**、かつ **同額程度のインクルードクレジット**が付与される説明が一般的（超過は従量）。帯域の超過例として **$0.15 / GB** 級の説明が第三者まとめで引用されることがあるが、**必ず公式の現在表を確認**。
- **Spend / 上限**: ドキュメントに **Plan retrieval / billing** や **overage**（Serverless 実行、画像最適化等）に関する列挙あり → ダッシュボードで利用量モニタ推奨。

**本プロダクト観点**: 仕様書の試算「Vercel **無料〜約 $20**」は、**Hobby で収まるトラフィックか**、**Pro が必要か**をデプロイ後の帯域・ビルド分で判断する形になります。

## 6. Railway（バックエンド API）

本仕様書ではバックエンドは Railway 上の FastAPI を想定しています（フロントの Vercel と分離）。

- **Pricing（公式）**: [railway.com/pricing](https://railway.com/pricing)（旧 URL [railway.app/pricing](https://railway.app/pricing) もリダイレクトあり）
- **Web 参照メモ（2026-04-11、[railway.com/pricing](https://railway.com/pricing) の記載）**  
  - **従量単価の例**: **Memory $0.00000386 / GB・秒**、**CPU $0.00000772 / vCPU・秒**、**Volume $0.00000006 / GB・秒**、**Egress $0.05 / GB**（サービスからの外向き転送）。  
  - **プラン**: ページ上に **30 日トライアル（$5 クレジット）**、トライアル後 **$1 / 月**の記載や、**月 $5 分・$20 分の利用クレジットがプランに含まれる**旨の説明が並ぶ。**プラン名と固定費は変更されやすい**ため、仕様書の「**$5〜$10**」は **「含まれるクレジット内に収まる軽量 API」の目安**と捉え、**実請求は Usage を正**にする。
- **課金ドライバー（概念）**: Railway では、一般に「**サービスを動かすためのリソース**（CPU/メモリ等）」「**ビルド**」「**ネットワーク（転送）**」などがコストに効きます（正確な内訳・単価・無料枠は公式 Pricing と Workspace の Usage を参照）。
- **運用の見方（ダッシュボード）**: ワークスペースの **Usage / Billing** で「今月の請求」「どのサービスが増えているか」を確認し、月次で §1.1 の集計に転記します。

**本プロダクト観点**（コストを上げやすい操作）

- PDF 解析・RAG 前処理などをバックエンドで重くやると、**API サービスの稼働リソース**が増えがち。
- ログを大量に出す、ビルド回数が増える、といった運用もコスト・上限に影響しうるため、運用ルール（ログレベル、デプロイ頻度）を決めておくと管理しやすい。

## 8. 監視・運用でやるとよいこと

1. **AWS**: Cost Explorer、タグ付け（Bedrock / S3）、必要なら予算アラート。Bedrock は公式ブログでも **アプリケーション別プロファイル**や **キャッシュ**の活用が推奨されています。
2. **Supabase**: Organization の [Usage](https://supabase.com/docs/guides/platform/billing-on-supabase) 画面で Egress・Disk・MAU を確認。Free の **500 MB DB** を超えると read-only になる旨のドキュメントあり。
3. **Vercel**: チームの Billing / Usage、プランに応じた Limits（アップロード回数等）を確認。
4. **Railway**: ワークスペースの利用量・請求を月次で確認（§1.1 の導線）。
5. **全体**: §1.1 のとおり、**真の「単一 UI」は各社にない**ため、月1回「4 箇所を開いて合計をメモ」するリズムを決めると、仕様の **月額目安（約 50 USD 以下）** と比較しやすいです。
