# 1. プロジェクト概要

## 1.1 背景・目的

| 項目 | 内容 |
|------|------|
| 対象ユーザー | 学部4年生（研究室配属後） |
| 開発形態 | 個人開発 → サービス展開 |
| コアバリュー | 論文読解・実験を円滑に進めることに特化 |
| スケーラビリティ | 考慮不要（小〜中規模ユーザー想定） |

## 1.2 ユーザーが抱える問題

```
論文関連
  ❶ 英語が難しくて読むのに時間がかかる
  ❷ どこが重要なのかわからない
  ❸ 専門用語が多くて意味がわからない
  ❹ 読んだ内容をすぐ忘れてしまう
  ❺ 複数の論文の違いを整理できない
  ❻ 論文のどこを読めばいいかわからない
  ❼ 内容を指導教員にうまく説明できない

実験関連
  ❽ 実験の進め方がわからない
  ❾ 実験結果の考察・分析に迷う
  ❿ エラー・バグの対処がわからない

卒論関連
  ⓫ 実験結果を卒論にどう落とし込むかわからない
```

## 1.3 インターフェース方針（UI/UX）

| 項目 | 内容 |
|------|------|
| **主役と従属** | **論文PDF（ページ）を主**とし、**チャットを副**とする。ユーザーの注意の中心は常にドキュメント側に置く。 |
| 体験モデル | 電子書籍・読書アプリに近い **ページ中心の読書体験** を基本とする（チャット全面型ではない）。 |
| 主な操作 | ページ送り・**拡大縮小**・**蛍光ペンに近いハイライト**（文章箇所のマーク）をPDFビューア上で行う。 |
| チャットの位置づけ | 読みながらの質問・解説のための **補助パネル**（サイドバー・ドロワー・下部シート等の具体レイアウトは実装時に決定）。 |
| 質問の起点 | テキストの**選択範囲**や**ハイライト**、**ページ位置**をチャットに引き継ぎ、「ここについて聞く」ができること。 |
| 図表 | 論文内の**図・グラフ**に対しても、領域を指定して質問でき、**軸・単位・数値の読み取り・解説**を求められること（詳細は F1-8）。 |
| デバイス | **PCに加えタブレット（iPad等）での利用**を想定する。**レスポンシブWeb**とし、タッチ操作（ピンチズーム、なぞり選択等）が破綻しないことを目標とする。**ネイティブモバイルアプリの開発は本仕様書の対象外**とする（将来検討可）。 |

## 2.2 技術スタック

| レイヤー | 採用技術 | 理由 |
|---------|---------|------|
| フロントエンド | **Next.js** | 扱いやすい・Vercelで簡単デプロイ |
| バックエンド | **Python FastAPI** | シンプル・軽量 |
| AI（生成・対話） | **Amazon Bedrock**（例：Claude 系、**Converse API**） | 会話管理が容易・**他モデルも同一ゲートウェイで利用** |
| AI（埋め込み） | **Amazon Bedrock**（Embeddings。利用可能なモデルはリージョン・提供状況に従い選定） | **RAG のベクトル化を Bedrock に統一**し、キー・課金・ガバナンスを一本化 |
| RAG | **LangChain + FAISS + Bedrock Embeddings** | 論文ベースの回答精度向上（ベクトルストアはローカル／マネージドは実装時に決定可） |
| DB | **Supabase（PostgreSQL）** | 無料枠あり・個人開発向き |
| ホスティング | **Vercel + Railway** | 低コストで運用可能 |
| 認証 | **Supabase Auth** | Supabaseと一体で管理が楽 |

### 2.3 モデル利用方針（Bedrock 統一）

| 項目 | 内容 |
|------|------|
| 方針 | **テキスト生成・対話・埋め込み（Embedding）・図表を扱うマルチモーダル推論**など、**マネージドAPIとして利用するモデルは Amazon Bedrock に統一**する。 |
| 目的 | 認証情報・ネットワーク境界・コスト・利用ログ・リージョンを **AWS 側に寄せて運用を単純化**する。 |
| 具体例 | チャット・要約・用語解説：**Bedrock のテキストモデル**（Converse 等）。RAG：**Bedrock の Embedding モデル**でチャンクをベクトル化し FAISS 等に格納。図表Q&A：**Bedrock 上で画像入力を受け付けるモデル**が利用可能なら同経路で扱う（不可の場合は仕様の「期待値」を実装時に再確認）。 |
| 例外 | **ローカル開発のみ**の軽量モデルや、**フロントにバンドルしない静的処理**など、Bedrock を呼ばない層はこの「統一」の対象外。本番経路の **AI 推論は Bedrock 前提**。 |

### 2.4 リポジトリ・ディレクトリ・環境変数（個人検証・非商用フェーズ）

| 項目 | 方針 |
|------|------|
| **ディレクトリ構成** | リポジトリ直下に **`frontend/`**（Next.js）と **`backend/`**（FastAPI）を置く。共有ドキュメント・スクリプトは `docs/` 等でよい。 |
| **シークレット・接続情報** | **`.env` / `.env.local`**（および各ホスティングの Environment Variables）で管理する。**秘密値は Git にコミットしない**。リポジトリには **`.env.example`**（キー名のみ・ダミー値）を置き、不足キーが分かるようにする。フロントに埋め込む値は **`NEXT_PUBLIC_` プレフィックス**に限定し、**AWS 秘密鍵・サービスロール鍵はバックエンドのみ**に置く。 |
| **実装計画** | 具体的なマイルストーン・API 設計・コスト画面の段階導入は **[実装計画.md](./実装計画.md)** に記載する。 |

### 2.5 単一リポジトリと分割リポジトリの選定

| 方式 | メリット | デメリット |
|------|----------|-------------|
| **単一リポジトリ（モノレポ）** | 個人開発で **仕様変更の連携が容易**、**1 つの CI** で frontend/backend をまとめて扱える、**クローン・Issue 管理が 1 箇所**で済む。 | リポジトリが大きくなりがち。権限をサービス単位で分けにくい。 |
| **frontend / backend を別リポジトリ** | デプロイ権限・公開範囲を分離しやすい。フロントだけ OSS 化などがしやすい。 | **型・API 契約の同期コスト**、**2 箇所の PR/Issue**、個人検証ではオーバーヘッドになりやすい。 |

**結論（個人検証・非商用）**: **単一リポジトリ + `frontend/` と `backend/` のディレクトリ分割を推奨**する。チーム拡大や別法人での公開など、**デプロイ主体を完全に分ける必要が出た時点**でバックエンドまたはフロントのみをリポジトリ分割してよい。

### 2.6 個人検証フェーズにおける認証・認可（保留）

| 項目 | 内容 |
|------|------|
| **方針** | **認証・認可の本格実装は保留**とする（**Supabase Auth・ロールベース制御は後続フェーズ**）。 |
| **目的** | 個人検証では **PDF ビューア・要約・Q&A・Bedrock 連携**に工数を集中する。 |
| **開発時の扱い** | **単一利用者想定**（開発者自身）とし、会話履歴・データは **同一テナント／開発用 DB** に格納してよい。画面からログインを要求しない構成、または **開発専用の簡易ガード**（環境変数フラグ・Basic 認証など）は [実装計画.md](./実装計画.md) に従い実装時に決定する。 |
| **本番・複数ユーザー** | **不特定多数への公開や研究室配属生の利用**に進む前に、**F4-2（ユーザー認証）を必須化**し、非機能要件の「ログイン認証」を満たす。 |

### 2.7 運用コストの可視化（管理画面）

| 項目 | 内容 |
|------|------|
| **概要** | 利用中の **Vercel / Railway / Supabase / AWS（Bedrock・S3 等）** について、**月次のコストを一覧・概算**できる **管理画面（または管理用ルート）** を設ける。 |
| **位置づけ** | 機能要件 **F4-3**（§3.5）。個人検証でも [運用コスト.md](./運用コスト.md) の **§1.1** で述べるとおり各社ダッシュボードは分散するため、**まとめて把握する UI** で開発者の負担を下げる。 |
| **精度** | **第 1 段階**は「公式ダッシュボードへのリンク＋手入力メモ」でもよい。**第 2 段階**で各社 **Billing/Usage API**（利用可能な範囲）や **AWS Cost Explorer** 連携で自動取得を追加する。詳細は [実装計画.md](./実装計画.md)。 |

### ❌ 採用しない技術（オーバースペック）

```
- AWS Lambda / ECS  → Railway で十分
- Amazon Kendra     → 高コスト・複雑すぎる
- Amazon Cognito    → Supabase Auth で代替
- Kubernetes        → 完全不要
```

### ❌ 本プロダクトの標準としないもの（モデルまわり）

```
- OpenAI API / Azure OpenAI を本番の「生成・Embedding の主経路」とする
  → 方針として Amazon Bedrock に統一（PoC 段階の一時利用は別途チームで判断可とするが、
    仕様上の正は Bedrock）
```

## 3.2 F1. 論文サポート機能（詳細）

### F1-0. 論文PDFビューア（ページ中心・読書体験）

| 項目 | 内容 |
|------|------|
| 概要 | アップロードした論文PDFを、**読書アプリと同様にページを中心に表示**するビューア。本プロダクトの**メイン画面**となる。 |
| 入力 | ユーザーがアップロードした **PDF**（F1-1 と共通の論文ソースと整合させる）。 |
| 表示 | **ページ単位**のレイアウト。現在ページの明示、前後への移動。 |
| 拡大縮小 | **ズーム**（ピンチ・ボタン・ホイール等）により活字・数式・キャプションを読みやすくする。 |
| ハイライト | **蛍光ペンに近いUX**で文章範囲をマーク可能とする。マークは後から参照・検索できるデータとして **F1-6** と連携する。 |
| チャットとの関係 | ビューアが**主画面**であり、チャットは **1.3** のとおり副（パネル／ドロワー等）。選択範囲・ハイライトから **F1-2** へ文脈を渡せること。 |

**UI原則（再掲）**
```
✅ ユーザーの視線と操作の起点は PDF（ページ）
✅ チャットは「読みながら聞く」ための補助
❌ チャット全面のみで論文を読ませる体験を主導線にしない
```

### F1-2. 論文Q&A（読みながら質問）

| 項目 | 内容 |
|------|------|
| 概要 | 論文を読みながらその場で質問できる。**F1-0 上のテキスト選択・ハイライト・現在ページ**を起点に、「この部分について」をチャットへ送れること。 |
| 特徴 | Converse APIの会話履歴機能で文脈を保持したまま質問可能。質問時には**選択テキスト・ページ番号・（実装可能な範囲で）周辺文脈**を会話コンテキストに含める。 |
| 技術 | **Amazon Bedrock**（Converse API 等。モデル選定は §2.3） |
| 備考 | **図・グラフのみ**を対象とする質問は **F1-8** で扱う。テキストと図が一体の説明の場合は F1-2 と F1-8 のいずれからでもよい（実装で統一可）。 |

**会話例**
```
User: この文の意味がわかりません
      ───────────────────────────────
      "We employ a multi-head self-attention
       mechanism to capture long-range
       dependencies"
      ───────────────────────────────

Bot:  わかりやすく説明します！

      📖 この文の意味
        「複数の視点で文章全体のつながりを
         把握する仕組みを使った」
        というイメージです。

      🔍 キーワード解説
        ├ multi-head    : 複数の視点で同時に見る
        ├ self-attention: 単語同士の関係性を計算する
        └ long-range    : 離れた位置の単語との
                          関係も捉えられる

      他にわからない箇所はありますか？
```

### F1-3. 専門用語解説（ハルシネーション対策あり）⭐ 重要

> #### 背景・課題
> ```
> AIが間違った説明をする（ハルシネーション）
>            ↓
> 学部4年生には正誤の判断が難しい
>            ↓
> 間違った知識のまま研究・卒論を進めてしまう
>            ↓
> 😱 大問題！
> ```

#### 対策の全体方針

```
ハルシネーション対策のアプローチ

① モデルに嘘をつかせない（生成側の対策）
         +
② ユーザーが気づける仕組みを作る（表示側の対策）
         +
③ 間違いを検知・蓄積する（検証側の対策）
```

---

#### 対策①：RAGで信頼できる情報源に基づいて回答

**仕組み**
```
【RAGなし（従来）】

User: 「アテンション機構とは？」
          ↓
    AIが学習データから
    「それっぽい」回答を生成  ← ハルシネーションの温床
          ↓
    回答（根拠不明）❌


【RAGあり（今回）】

User: 「アテンション機構とは？」
          ↓
    ① 信頼できるデータソースを検索
       - アップロードされた論文のテキスト
       - 教科書・信頼性の高い技術文書
          ↓
    ② 検索結果を根拠に回答を生成
          ↓
    回答（出典付き）✅
```

**信頼できるデータソース候補**

| ソース | 特徴 | 優先度 |
|--------|------|--------|
| ユーザーがアップロードした論文 | 文脈に直結 | ⭐⭐⭐⭐⭐ |
| arXiv の該当論文 | 最新・権威あり | ⭐⭐⭐⭐ |
| 教科書PDF（許諾あり） | 正確性が高い | ⭐⭐⭐⭐⭐ |
| Wikipedia（英語） | 広範囲をカバー | ⭐⭐⭐ |
| 技術ブログ（Qiita等） | わかりやすいが精度にばらつき | ⭐⭐ |

#### 対策②：出典の必須表示 + 信頼度スコアの可視化

**信頼度の判定基準**

```
⭐⭐⭐⭐⭐  信頼度：高

```
✅ Phase 1 でリリースする機能（個人検証・非商用の主線）
  - 論文PDFビューア（ページ表示・ズームの最低限。レイアウトは「PDF主・チャット副」）

  - 論文要約（PDF → 日本語要約）
  - 論文Q&A（論文の文脈を保持した質問。可能なら選択テキスト起点）

⏸ 個人検証フェーズでは保留（本番前に必須化）
  - ユーザー認証・認可（F4-2、Supabase Auth 本格実装）※§2.6

❌ Phase 1 では作らないもの（または簡易版に留める）
  - 専門用語解説のRAG対策（Phase 2）
  - ハイライトの永続化・一覧の本格実装、図表Q&Aの高度化（Phase 2〜3 で段階導入を検討）
  - 論文比較・メモ管理の拡張（Phase 3）
  - 実験サポート機能（Phase 4）
  - 卒論サポート機能（Phase 5）
```

# 7. まとめ

```
このチャットボットが解決すること

Before（現状）                 After（導入後）
──────────────────────────────────────────────────
英語論文が読めない         →  ページ中心で読みながら、日本語で要約・解説
重要箇所がわからない       →  ハイライト・選択質問＋構造化要約で整理
用語がわからない           →  専門用語解説（出典付き）
用語解説が正しいか不安     →  信頼度スコア + 出典表示
複数論文の整理に困る       →  比較表で一発整理
読み方がわからない         →  読解ガイドで手順を提示
実験の考察に迷う           →  改善案をAIが提示
エラーが解決できない       →  エラー内容を貼れば解決策
卒論への落とし込み方不明   →  結果から卒論草案を自動生成
```
