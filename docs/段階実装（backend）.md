## 1. バックエンドの論理構成（software-architecture）

| 観点 | 方針 |
|------|------|
| **量子との関係** | デプロイ単位は **Railway 上の backend サービス 1 つ**として扱う。フロント（Vercel）とは **別 Quantum** だが、**製品としては 1 ドメイン**；過早なサービス分割（マイクロサービス化）はしない。 |
| **レイヤリング** | **HTTP 境界（ルータ・スキーマ）**、**ユースケース／ドメイン**、**外部クライアント（Bedrock・S3 等）**の責務を混同しない。**コスト用 Billing API は ADR-002 に従い `frontend` の server-only で扱い、Python には置かない**。外部レスポンスは **境界で検証・正規化**し、深部に生の辞書や `Any` を垂れ流さない。 |
| **同期通信をデフォルト** | メイン機能は **リクエスト／レスポンス**で十分な範囲から始める。長時間ジョブが必要になった時点で **バックグラウンドタスク＋ポーリング**等を ADR で検討する。 |
| **ADR が効くタイミング** | 例: **Bedrock 呼び出しのエラーポリシー**（リトライ・サーキットブレーカー）、**PDF の保存先**（一時ストレージ vs オブジェクトストレージ）、**認証保留中のガード方式**（論文 API 側）。コスト HTTP API は **FastAPI に置かない**（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。索引は [docs/adr/README.md](./adr/README.md)。 |
| **Architecture Slop 回避** | 「常にマイクロサービス」「常にイベント駆動」に寄せない。**個人検証のチーム規模・運用コスト**に見合う **モジュラなモノリス（`backend/` 内モジュール分割）**を既定とする。 |

## 2. Python 品質の横断方針（robust-python）

| 領域 | 方針 |
|------|------|
| **型** | 公開関数は **引数・戻り値に型**。**`Any` は原則禁止**（例外時は理由をコメント）。**Optional** は「値がない」に限定し、**成功／失敗**は **Union（Sum 型）や Result 相当**で表現する余地を検討する。 |
| **境界** | リクエスト／クエリは **Pydantic** で受け、**ドメインに入る前に検証**する。外部 API の JSON は **スキーマ検証**（Pydantic、`TypeAdapter` 等）で **unknown に近い入力**を扱う。 |
| **拡張** | **コスト自動取得**は TypeScript 側の責務（ADR-002）。Python は **Bedrock・PDF・論文ドメイン**の拡張に **`Protocol` / コンポジション**を使う（過早な `if provider == "x"` 連鎖を避ける）。 |
| **OCP / 分離** | 再試行・タイムアウト・ロギングなど **横断関心**はビジネス関数に埋め込みすぎず、**デコレータ・ミドルウェア・薄いラッパ**で分離できるか検討する。 |
| **セーフティネット** | **Pyright または mypy** を CI または pre-commit のどちらかに載せる。**pytest** は M0〜M1 から最低限回せるようにする（後述 §6）。 |
| **Python Slop 回避** | `except Exception` の一律ログ、**dataclass 乱用**、**モックだらけの単体テスト**に陥っていないか、フェーズ完了時にセルフチェックする。 |

## 3. Railway 運用（use-railway）

| 項目 | 方針 |
|------|------|
| **コンテキスト** | 操作前に **`railway status --json`** / **`railway whoami --json`** で **Project / Environment / Service** を確認する。ユーザーから **ダッシュボード URL** が渡された場合は **その URL の ID を正**とし、ローカルの link と取り違えない。 |
| **モノレポ** | `backend/` のみをデプロイする場合、**Root Directory** を **`backend`** に合わせる（実装計画 §5.4）。ビルドコマンド・起動コマンドが **リポジトリルート基準かサービスルート基準か**を README と Railway 設定で一致させる。 |
| **変数** | ローカル `.env` と **Railway Variables** の **キー名を揃える**。`AWS_*`・`BEDROCK_*` 等は **backend のみ**（フロントに漏らさない）。変更後は **`railway variable list`**（またはダッシュボード）で読み戻し確認。 |
| **観測** | 不具合時は **`railway logs`**（サービス明示が必要なら **`--service`**）で **ビルド失敗とランタイム失敗**を切り分ける。 |
| **破壊的操作** | DB や拡張のインストール等、スキルが **ユーザー専用コマンド**とするものは、エージェントが代行せず **手順とコマンドを文書化**する。 |

## 4. 段階一覧と実装計画マイルストーンの対応

| 本書フェーズ | 主に対応するマイルストーン | 一言サマリー |
|-------------|---------------------------|-------------|
| **BE-0** | M0 | 足場・依存関係・品質ゲートの土台 |
| **BE-1** | M1 | ヘルス API・CORS・Railway 空デプロイ・変数配線 |
| **BE-2** | M2 | Bedrock（要約または短いチャット）をバックエンド経由で 1 通成功 |
| **BE-3** | M3 | PDF の受け渡し（アップロード or URL 取得）とストレージ方針の最小実装 |
| **BE-4** | M4 | **コスト API は実装しない**（Route Handler 担当）。並行して **論文・PDF・Bedrock** の安定化に振れる |
| **BE-5** | M5 | Phase 1 MVP に寄せた **要約・Q&A** の API とエラーポリシー |

並行作業: **FE-4（コスト UI・Route Handler）と BE-3（PDF 等）は独立**しやすい。**BE-4 はバックエンドにコストを書かない**ため、M4 では **FE-4 + BE-3 の並行**を優先してよい（実装計画 §8 と同旨）。

## 5. フェーズ別ガイド（コードなし）

### BE-0：足場（M0）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | `backend` が単体で起動・テスト実行できる構成。**依存の方向**（ルータ → ユースケース → 外部）を乱さない初期配置を決める。 |
| **robust-python** | パッケージレイアウトと **型チェッカ設定**（Pyright / mypy）を有効化する方針を決める。**新規モジュールから `Any` 禁止**を徹底。 |
| **use-railway** | 将来のサービス名・環境名の **命名規則**だけ決めて README に書く（まだリンクしなくてよい）。 |
| **test** | **pytest が 1 本でも green** になるよう、自明な純粋関数または「インポートできる」レベルから開始（**4 本柱**で価値のないテストだけ量産しない）。 |
| **review** | `.env` がコミットされていないか、**秘密のサンプルが README に載っていないか**を確認（review 3d 相当）。 |
| **完了条件** | ローカルで **サーバ起動 + pytest + 型チェック**が通る。`.env.example` と整合。 |

### BE-1：疎通（M1）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | **ヘルスチェック**を 1 本用意し、フロント・監視・Railway のヘルスチェック URL と整合。必要なら **CORS 許可**を環境別に限定する方針を ADR メモに残す。 |
| **robust-python** | 設定値は **Pydantic Settings** 等で **型付き読み込み**し、起動時に **必須キー欠落を明示的に失敗**させる。 |
| **use-railway** | **Root Directory**・**Start Command**・**Variables** を設定し、**本番相当 URL** でヘルスが返ることを確認。デプロイ後 **`railway logs`** で起動エラーを潰す。 |
| **test** | ヘルスエンドポイントは **統合テスト**（`TestClient` 等）で **振る舞い**を検証。**実装詳細**ではなく **ステータスと契約**に寄せる（test スキル・リファクタリング耐性）。 |
| **review** | **本番 URL** が公開された時点で、**不要なデバッグ出力・スタックトレース露出**がないか確認（review 3a / 3d）。 |
| **完了条件** | フロントまたは curl から **本番相当パスで到達**。Railway で **再デプロイ後も同じ確認手順**が使える。 |

### BE-2：AI（Bedrock）（M2）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | **Bedrock クライアント**を **インフラ層**に閉じ、ユースケースは **インターフェース越し**に呼ぶ。タイムアウト・リトライ方針を **1 箇所**に集約。 |
| **robust-python** | モデル ID・リージョンは **定数／設定**に集約。**レスポンスのパース**は境界で行い、**失敗**は **型で表現**（例外のみに依存しない選択肢を検討）。 |
| **test** | Bedrock 実呼び出しは **コストと不安定性**があるため、**ユースケース単体テストは Fake／スタブ**、**スモークは手動または隔離された 1 本**に分ける（test スキル・境界でのモック）。 |
| **review** | **ログにプロンプト全文・PII**を出していないか、**エラーメッセージに AWS 内部 ID**が露出していないか（review 3d）。 |
| **完了条件** | **エンドツーエンドで 1 回以上**、バックエンド経由でモデル応答が返る。 |

### BE-3：PDF コア（M3）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | **ファイルサイズ上限**・**MIME 検証**・**一時ファイルの掃除**を設計に含める。S3 等を使う場合は **バケットポリシーと IAM** を ADR に残す。 |
| **robust-python** | アップロードボディは **ストリーミングとバッファ**のトレードオフを決め、**メモリ枯渇**を防ぐ。パス・URL は **専用型または NewType** で混線を防ぐ余地を検討。 |
| **test** | **小さな PDF フィクスチャ**または **生成バイト列**で **ハッピーパス**と **異常系**（空・巨大・不正形式）を分離。**モックは外部ストレージ境界のみ**（test スキル）。 |
| **review** | **パストラバーサル**、**公開 URL の推測可能性**、**認証保留中の無制限アップロード**（review 3c / 3d）。 |
| **完了条件** | フロントまたは API クライアントから **PDF が取得・表示可能なデータ**が返る（実装計画 M3 と整合）。 |

### BE-4：M4（コストはバックエンド外）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | F4-3 の **HTTP API・永続化は Next.js Route Handler**（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。FastAPI に **コスト用ルートを追加しない**ことをレビューで確認する。 |
| **robust-python** | M4 スプリントでは **論文 API**（PDF・Bedrock・バリデーション）の **品質・テスト**を優先してもよい。 |
| **use-railway** | バックエンドのデプロイ・変数は **論文用**に集中。**コスト用シークレットは Railway に置かない**運用でよい（Vercel に集約）。 |
| **test** | **コスト API のテストは `frontend` 側**（Route Handler の統合テスト等）。Python 側は **回帰のないこと**を確認。 |
| **review** | **誤って `backend` にコストエンドポイントが生えていないか**、**二重実装になっていないか**。 |
| **完了条件** | バックエンドとして **コスト API を持たない**状態が維持され、[段階実装（frontend）.md](./段階実装（frontend）.md) の FE-4 と **実装計画 M4** がフロント側で満たされる。 |

### BE-5：MVP 寄せ（要約・Q&A）（M5）

| 観点 | やることの例 |
|------|----------------|
| **software-architecture** | **要約・Q&A** の **セッション／コンテキスト ID**（将来の `user_id` 拡張を見越し）を **単一テナント**でも一貫して扱う（実装計画 §7）。 |
| **robust-python** | **長文入力**・**トークン制限**に対する **明示的エラー**と **ログレベル**を揃える。**Bedrock のスロットリング**時のユーザー向けメッセージを定型化。 |
| **test** | **ドメイン重要度が高い純粋関数**（チャンク分割、プロンプト組み立てのうち決定的な部分）を **出力値ベース**で優先。E2E は **最小シナリオ 1 本**に留める（test ピラミッド）。 |
| **review** | **仕様書 MVP** との **Semantic drift**（パラメータ名・必須フィールド・エラーコード）をクロスチェック（review 3a）。 |
| **完了条件** | 仕様書 **Phase 1** のバックエンド側要件を満たす（認証は引き続き保留でよい）。 |

## 6. 第 2 段階（コスト自動取得）とバックエンドの関係

実装計画 §6.2 の **プロバイダ別アダプタ**は **`frontend` の server-only（TypeScript）**に置く（[ADR-002](./adr/ADR-002-cost-api-nextjs-route-handler.md)）。**Python バックエンドでは実装しない。**

| 観点 | 方針 |
|------|------|
| **software-architecture** | Railway 上の FastAPI は **論文・Bedrock・PDF** のスコープに専念。コスト同期の **タイムアウト・レート制限**は Next／Vercel 側の設計事項。 |
| **robust-python** | 該当なし（コスト自動取得コードを Python に **置かない**）。 |
| **use-railway** | **Billing 用トークンを Railway に載せない**方針でよい。**ログに誤ってトークンが出ていないか**は Vercel 側で確認。 |
| **test** | アダプタの **単体・統合テストは frontend リポジトリ**で行う。 |
| **review** | **Python にコスト取得が漏れていないか**（責務の逸脱）。 |

## 7. フィットネス関数（バックエンド）

| タイミング | 例 |
|------------|-----|
| **コミット前／CI** | **pytest**（失敗でブロック）、**Pyright または mypy**、（任意）**ruff** / **bandit**。 |
| **デプロイ前** | **Railway ビルド成功**、**起動時ヘルス**、**必須環境変数**の欠落がないこと。 |
| **レビュー時** | review スキルの **仕様乖離・境界値・機密・テスト品質**を意識。robust-python の **Slop（RP-1〜RP-6）**が増えていないか。 |
